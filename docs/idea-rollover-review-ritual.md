## Idea Brief: Rollover as a Review Ritual (the threshold, not the footnote)

**Problem:** Bullet journaling's engine is *migration*. At the top of a new week or month you re-copy your unfinished items by hand, and the friction of re-copying forces a small re-decision on each one: does this still deserve to exist, or has it quietly died? The copying is the medium; the *re-deciding* is the point. Homebase already automates the copying with carry-over: expand a fresh week and last week's text is pre-loaded for you. That is a genuine convenience, and it silently removes the re-decision moment. The text arrives intact, you glance at it, you keep writing. Nothing ever made you look at last week and ask "what carries, what is done, what do I drop?" The most valuable moment in the practice has been optimized away.

**Solution:** The first time a user opens Homebase in a *new period* (a new week, a new month, a new year), treat that open as a **review threshold**, not an ordinary load. Instead of the fresh horizon sitting collapsed like any other row, land the user with that rolled-over horizon **already expanded**, last period's carried text visible, and an invitation with teeth above it: *"New week. Here is what last week was for. What still carries? What is done? What do you drop?"* One screen. No wizard, no multi-step flow, no modal stack. It is the same accordion the user already knows, opened to the one row that just crossed a boundary, with its register promoted from marginalia to threshold for this one visit.

This is not a new subsystem. `CarryOverResolver` already knows *exactly* when this moment occurs, because carry-over is defined as "first time entering a new period." The whole idea is to promote that knowledge from a quiet footnote (the `CarryOverBanner` asterisk in the margin) to a deliberate threshold the user crosses on purpose.

**For whom:** Brandon first, then anyone who keeps a Homebase and came to it from a paper practice (bullet journal, weekly review, GTD). People who already believe in the review ritual and chose a tool that was quietly doing the copying *for* them without giving back the re-decision. The threshold hands that decision back.

**Why now:** Carry-over shipped and works (PR-era `CarryOverResolver` + `CarryOverBanner`), which means the mechanism that detects "new period" is already built and tested. The only thing missing is the choice to *use that detection for a moment of reflection* rather than only for pre-loading text. Nothing new has to be discovered; a register has to be turned up. It also sets up Brief 2 (`docs/idea-scheduled-reflection.md`): once there is a rhythmic threshold at each new period, the AI reflection moment has a natural home to live inside, instead of a footer link nobody remembers.

## The core reframe: carry-over is already the detector

The insight that makes this cheap: **the condition "first open in a new period" is the exact condition carry-over already resolves.** Read the header comment in `homebase/src/lib/carry-over-resolver.ts`:

> The caller is responsible for not calling this when the target file already exists. Carry-over is a *first-time-entering-a-new-period* concern.

So the resolver returns a non-null `CarryOver` (with `content` and `sourcePeriod`) precisely when the user is standing on a threshold: a new week/month/year exists as a period, no file has been written for it yet, and there is a prior period to carry from. That non-null result *is* the threshold signal. The current UI treats it as "show a small banner"; the idea treats it as "this is a review moment, stage the screen for it."

## Mechanics

1. **Detecting "first open in a new period."** There are two candidate signals, and the honest answer is to use both, layered.
   - **The file-absence signal (already built).** `CarryOverResolver.resolve(fs, horizon, targetPeriod)` returns non-null exactly when the target period has no file yet but a prior one exists. This is the *authoritative* signal that a horizon has crossed into a new period the user has not yet written into. It needs no new state; it is derived from the filesystem.
   - **The last-seen-period signal (new, tiny).** The file-absence signal alone cannot answer "is this the *first* time the user has landed on `/` since the boundary?" It stays true until the user writes something. If we staged the threshold on every load while the period file is still empty, we would re-open the review screen every visit until they type, which is a nag. So add a small `localStorage` key, e.g. `homebase.lastSeenPeriod.week` holding the last period key the user was shown a threshold for. On load, compare it against `PeriodKey.current("week")` (from `homebase/src/lib/period-key.ts`). If the current key is newer than the stored one *and* the resolver confirms carried content exists, stage the threshold and write the new key back. After that, subsequent loads in the same period are ordinary. This is the same localStorage-flag pattern `Masthead.tsx` already uses for `homebase.seenIntro`, so it is a familiar seam, not a new idea.

   Layering matters: last-seen alone would fire even when there is nothing to review (brand-new user, no prior period); the resolver alone would fire repeatedly. The AND of the two is "a real boundary, shown once."

2. **Which horizon(s) to surface.** Three horizons roll: `year`, `month`, `week` (the `TIME_BOUND_HORIZONS` set in the resolver; life-values and life-goals are persistent and never roll). On any given day at most one *new* boundary is usually crossed, but they can stack: the first Monday of a month that begins a new week, month, and (rarely) year at once. The calm default is **surface the shortest-horizon boundary that just crossed, one at a time**, because week is the horizon a person actually re-decides most often and the one whose review is a weekly habit. If month or year also just crossed, note it lightly ("a new month also began") but do not open three rows expanded at once. That is how one screen stays one screen. Surfacing every crossed horizon at full register would recreate the wizard we are explicitly refusing.

3. **What the staged screen looks like.** Reuse the existing accordion on `/` (`homebase/src/routes/index.tsx`, `StrategyAccordion`). The change is: on a detected threshold, the relevant `HorizonRow` mounts *expanded* with its carried content shown, and instead of the quiet `CarryOverBanner` marginalia, it shows the threshold invitation in a stronger register (the same visual family as `HorizonInvitation`, but phrased as a review prompt with the three questions). The rest of the accordion stays exactly as it is behind it, so the user's context is intact and one click collapses the threshold back to the ordinary cover. No route, no modal: the threshold *is* the cover, opened to the right place.

4. **Keeping it one calm screen, not a nag.** Three guardrails.
   - **Once per boundary.** The last-seen-period key guarantees the threshold shows once per new period, then reverts to the ordinary banner. Writing into the period (the first `setContent`, which already clears `carryOver` in the store) also ends the threshold naturally.
   - **Dismissible without penalty.** Collapsing the row or clicking away is a complete, valid response. "I looked, nothing to change" is a real outcome of a review. The threshold must never block the rest of the app or demand text before it yields.
   - **Deictic, not accusatory copy.** "Here is what last week was for. What carries?" invites; "You have unfinished items from last week" scolds. The whole value evaporates if the screen reads as a chore-list the app is nagging you to clear.

5. **What it does NOT do.** It does not diff last period against this period, does not check items off, does not track completion state, does not require the user to categorize each line. Bullet journaling's re-decision is a *human* act of re-reading and re-copying (or choosing not to). We stage the moment and get out of the way. Adding item-level state would rebuild a task manager inside a journal, which is the opposite of the ethos.

## The honest risk

The thing that could kill this is that **a forced review moment becomes friction people dread.** Paper migration works partly because it is voluntary and physical; a screen that greets you with "what did you fail to finish?" every Monday can curdle into the app that makes you feel behind. Three mitigations are baked into the mechanics above (once-per-boundary, freely dismissible, invitational copy), but the deeper answer is that this is a *lived-experience* bet, exactly like the one `docs/idea-reflection-slots.md` makes about inference: build the shape, use it, and let real weeks tell you whether the threshold earns its interruption. If after a month of real use it feels like a nag rather than a threshold, the fallback is graceful: turn the staging off and the `CarryOverBanner` footnote is still there, unchanged, doing what it does today. Nothing is lost by trying, because the underlying carry-over mechanism is untouched; we are only choosing whether to promote its register on first open.

## File pointers (the real seams)

- **The threshold detector already exists:** `homebase/src/lib/carry-over-resolver.ts`. `CarryOverResolver.resolve()` returns non-null exactly on a first-open-in-new-period. No change needed to *detect*; the change is what we do with the signal.
- **Current (footnote) register:** `homebase/src/components/CarryOverBanner.tsx`. This is the marginalia we are promoting. Keep it as the fallback register for ordinary in-period visits; add the stronger threshold register for the first open.
- **Where the horizon renders and would stage expanded:** `homebase/src/components/HorizonRow.tsx`. `StrategyRow` already reads `row.carryOver`, mounts `CarryOverBanner` when non-null, and renders `HorizonInvitation` for empty rows. The threshold is a third branch here: when the boundary is fresh, mount expanded with the review-invitation copy instead of the quiet banner.
- **Where staging is decided on load:** `homebase/src/routes/index.tsx`, `StrategyAccordion`. This is where a `useEffect` would compare `PeriodKey.current(...)` against the `homebase.lastSeenPeriod.*` localStorage keys and, on a real boundary, tell the store to open the relevant row expanded in threshold mode.
- **Period math:** `homebase/src/lib/period-key.ts`. `PeriodKey.current(horizon)` gives the current key; the last-seen comparison is a string compare of period keys (they sort lexicographically by design, per the resolver's step-2 fallback).
- **Precedent for the localStorage-once pattern:** `homebase/src/components/Masthead.tsx`, the `homebase.seenIntro` flag. Same shape: show a thing once, remember we showed it, don't show it again.
- **Store seam:** `homebase/src/store/strategy.ts`. `expandRow`, `clearCarryOver`, and the per-row `carryOver` field already exist; the store may need a way to open a row *expanded in threshold mode* rather than the current expand-on-click.

## Post-MVP knobs (roadmap, not now)

1. **Stacked-boundary handling.** When week, month, and year cross on the same day, offer a gentle "review your month too?" step *after* the week threshold is dismissed, rather than opening them together. Only build this once single-horizon staging has proven it is wanted.
2. **A review artifact.** Optionally write a tiny dated note when a threshold is completed ("reviewed week 2026-W26, carried 2 items, dropped 1"), so the practice leaves a trail the way paper does. Purely additive; skip until the ritual itself is validated.
3. **The reflection fusion (Brief 2).** The threshold is the natural home for the AI reflection moment. See `docs/idea-scheduled-reflection.md`: at the review threshold, alongside "what carries / what is done," offer one button to reflect on last period with an AI. That brief depends on this one's rollover detection.
4. **Cadence honesty toggle.** If real use shows the weekly threshold is welcome but the yearly one feels heavy, let the cadence be per-horizon (always stage week, ask before staging year). A knob, not a rebuild.
